Purpose and boundaries

The guide helps someone continue a research project after the person who wrote its code has moved on. A useful answer might identify a trusted figure, a manual step, an abandoned method or an unresolved question. A few honest notes are a successful handover.

Keep writing on one page, allow questions in any order, and let the researcher export from anywhere. The Write and Preview tabs use the same draft. A realistic project may have a notebook and some data files, with no package, version history or tests of its own.

For a new development session, read the relevant section here, inspect the corresponding source, and run the locked tests. The project’s source of truth for the questionnaire is data/guide.yaml. A researcher’s exported HANDOVER.md is research context.

Working locally

pixi install --locked
pixi run serve
pixi run docs
pixi run test
pixi run build

Use separate terminals for the site and documentation servers. The guide runs on port 1313 and these docs on port 1314. Both commands serve from memory. The production build writes to public/. Pixi supplies Hugo, Node.js and the GitHub CLI for all supported platforms.

This page is ordinary HTML and can also be opened directly from docs/index.html. The small Hugo configuration in docs/ serves only this page. The main Hugo project and both deployment jobs publish the researcher-facing site.

Architecture

Hugo reads the YAML and renders a complete, labelled form. At page load, the browser reads the stable field IDs, labels and chapter order from that form. The preview, clipboard and download all call the same Markdown writer.

data/guide.yaml and data/interface.yaml
The first file owns the chapters, question bank, project fields, introduction and interchange version. The second owns navigation labels, prompts for operating the interface and status messages.
data/reading.yaml and content/references.md
The content file establishes the public route. The YAML holds the reading list, situations, attribution and local thumbnail names. Match each group to a stable chapter ID. Use primary sources, check the destination and asset licence, and keep source and licence links in the image credits. The reading page shares the main site’s colour preference and never opens the draft store.
layouts/home.html and layouts/_partials/
The templates build semantic HTML from those files. The chapter partial resolves IDs from the question bank. Global assets use Hugo resource permalinks so deployments under a project path load correctly.
assets/js/app.mjs
Connects the controls to draft storage and file operations. It manages tab and chapter navigation, confirmation dialogs, drag-and-drop and accessible feedback.
assets/js/markdown.mjs
Converts a guide and a map of field values to deterministic Markdown, and parses a versioned file back into values. This module runs independently of the browser.
assets/js/draft.mjs and assets/js/files.mjs
The draft store reads and writes browser storage. File helpers copy text, display raw Markdown and download a UTF-8 blob. The application keeps all three operations local.
data/personas.yaml, writing.mjs, preferences.mjs, appearance.mjs and scope.mjs
Persona text is keyed by permanent chapter and prompt IDs. Missing translations use the Field Notes wording. The browser captures canonical export headings before applying a persona. Preferences are stored separately from answers. Scope choices affect navigation and the coverage denominator. An answered chapter always stays applicable.
assets/js/preview.mjs and assets/vendor/
The source view, copy and download share one writer. The rendered view removes the interchange header, parses the body with Marked, escapes raw HTML, substitutes image alt text, and sanitises the result with DOMPurify. Libraries ship with the site. See static/third-party/ for package versions and licences. To update, fetch the pinned npm tarballs with npm pack --ignore-scripts, compare their integrity against the registry, copy the ESM files named in versions.txt, and refresh the licences. Run the preview tests and check in a browser that an image in a draft makes zero network requests.
assets/guide.css and assets/*.svg
The stylesheet defines notebook colors, typography, focus indicators, writing surfaces and responsive navigation. The book illustration, chapter symbols and favicon are local assets.

Regrouping questions

During a workshop, move a question by cutting its ID from one chapter’s questions list and pasting it into another. The question bank contains its wording once. An answer is keyed by question ID, so moving or rewording the question preserves its connection to the draft.

  1. For a new prompt, add a fresh ID in the question bank with its text. Add help, an example or a list of references when they help someone answer.
  2. List the ID once in the desired chapter. Use lowercase, hyphen-separated IDs. Give a genuinely different research question a new ID.
  3. Set the chapter’s characterful title and a descriptive subtitle. The subtitle appears as a heading in the exported document. The order in YAML drives both the form and the document.
  4. To set a question aside, remove it from the chapter list. Ordinary edits retain its stored answer. Relisting its ID makes the answer visible again.

Give one prompt per chapter a short quick question for Speedrun. After regrouping, the first marked prompt in each chapter wins. A chapter without a marked prompt uses its first question. Set tags to the relevant technical, personal or ethical topics. Each applicable prompt counts once per listed topic, across the full questionnaire. Put any opt-out wording in the chapter’s scope and omit keys. Personalised labels and alternate quick prompts go in data/personas.yaml.

When retiring an answered question permanently, consider how people with existing files will recover their work. The importer reports an unknown question before applying any changes. Their original Markdown contains the full answer.

Drafts and privacy

The storage key includes a namespace, storage version and deployment path. Within the stored object, project. prefixes metadata and answer. prefixes question IDs. A normal edit reads the latest draft and patches the edited fields. A confirmed replacement writes one complete snapshot.

Keep raw input intact. Whitespace determines whether a response has content, but the writer keeps the original text for every included response. A failed write leaves the edits in memory and displays a warning. A later successful write retries pending edits. Export remains available while storage is blocked.

Use text nodes or control values for researcher input. The production page restricts network connections and form submission. Browsing, dropping and pasting an exported file use the same version check and confirmation before replacing a draft.

Markdown interchange

The exporter writes a short YAML header followed by the project metadata and answered questions. handover_version identifies the interchange format and question_order identifies the responses in body order. Each answer appears once as ordinary Markdown. Stable IDs let a later form use newer wording or a different grouping.

Thematic breaks separate answer records. The writer chooses a break length absent from the answer text. The reader looks for that break before a question heading, so a researcher’s own headings, code blocks and dividers survive a round trip. Import accepts UTF-8 files with a byte-order mark and Windows line endings.

Change formatVersion for incompatible changes to the interchange contract. Regrouping alone needs no version bump. A supported file can be edited by hand if its record order, headings, boundaries and header stay intact. On a version mismatch, report the file’s version and the expected version, and keep the current draft available.

Verifying changes

pixi run test uses Node’s built-in test runner. The fixtures deliberately have different question counts from the live form. Build tests exercise the current site at a root URL and a nested URL, verify form labels and anchors, and build an alternative grouping.

  • For a format change, test omissions, leading and trailing whitespace, multiline code, ordinary hand edits, uploads after regrouping and rejection of incompatible files.
  • For a storage or interaction change, try a real reload, denied storage, a failed clipboard write, cancellation, download and opening the downloaded file through both upload paths.
  • For a layout change, check keyboard focus, the tab arrow keys, mobile chapter links, the persistent export control and horizontal reflow at 320 CSS pixels.

Keep edits to workshop questions independent of the layouts and JavaScript. Preserve stable IDs and add a small regression test when a change exposes an untested failure.

Publishing and attribution

GitLab uses .gitlab-ci.yml and CI_PAGES_URL. GitHub uses .github/workflows/pages.yml and the base URL returned by its Pages configuration action. Both run the Pixi tests and use the production build on the default branch. Only public/ is selected for deployment.

Keep developer material under docs/. Adding it to the main site’s static/, content/ or asset pipeline would publish it. The production tests check that the generated site contains the questionnaire, references and About pages. Edit the project story and team credits in content/about.md.

The repository’s LICENSE covers the MIT-licensed site and illustrations. The team records AI involvement in aidecl.yaml. When that involvement changes, update the declaration and check it with aidecl validate aidecl.yaml. Researchers retain ownership of their exported notes.
